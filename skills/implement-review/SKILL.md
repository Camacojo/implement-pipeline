Read `PIPELINE.md` in the `implement` skill directory (`../implement/PIPELINE.md` relative to this skill's base directory) first. Input: the diff of the change, **exported to `<state dir>/diff-<round>.patch` and passed to every reviewer by path** — never "the current changes" or "the branch": in a feedback round the diff is only what changed since the previous round's commit (`git diff <last round commit>..HEAD` plus the working tree), otherwise reviewers re-review round-1 decisions. `spec.md`, `contracts.md`, the project docs. Standalone on a PR: use the PR description as the spec. Writes `review.md`.

## Phase 8 — Code review

Run both in parallel, then merge into `review.md`:

0. **Decide the review set first**, and write it in `review.md`: one fresh reviewer per *layer the change actually touches* (a backend service and a page are two layers; two services of the same kind are one), plus the built-in skill only under the rule below. Do not add reviewers because the size class is L.

1. **Review skills** — the built-in `code-review` skill (effort `medium` for S/M, `high` for L) and any language- or project-specific review skill the session offers. Give the skill the patch path as its target and state the scope in one sentence; if its findings drift outside the patch, send it one message to narrow the scope and drop the out-of-scope items. Run the built-in skill when the change touches cross-cutting output or infrastructure (logging, error tracking, messaging, serialization, config, security); for business logic, even across two layers, the layer-scoped fresh reviewers alone are enough, because each already reads its whole layer. The built-in skill's per-finding verification costs roughly ten minutes at `medium` and it may return a partial report; merge what it delivers.
2. **Fresh reviewer agent(s)** — read-only brief (ground rule 9): the diff, `spec.md`, the relevant project-docs sections, the review checklist. One reviewer per package for L. The brief has **two named parts**, so the reviewer spends its steps where they pay:
   - **Part A, checklist (fast):** consistency with surrounding code and patterns; project code conventions; architecture and application rules; AC coverage; test quality (behaviour, not implementation; discriminating negative assertions; no weakened assertions). Verify by reading the diff and the changed files only.
   - **Part A+, the project's failure catalogue:** the review checklist in the project docs lists the mistakes this codebase has actually made (globally scoped styles, flags set before their guard, assertions that restate their fixture, …). Check the diff against that list by name before anything else — a repeat is the cheapest finding there is, and a pipeline easily produces the same class of bug in consecutive runs.
   - **Part B, blast radius (targeted):** "what outside the diff consumes or transforms what this change produces?" — with an explicit list of where to look, written by the orchestrator from the plan: log processors and handlers, framework listeners/subscribers on the same event, config that filters or routes the output (monitoring, error tracking, messaging), serializers and API contracts, jobs/consumers reading the same data. The reviewer checks those places and stops; it does not explore beyond the list unless it finds a concrete lead.
   Part B is the part that finds regressions tests-first cannot see (blocking findings typically sit outside the diff); Part A alone is enough for changes confined to one service with no cross-cutting output.
   Ask for findings with the mechanism stated in one or two sentences and a file:line; do not ask for exhaustive proof from vendor sources — the orchestrator asks for that only when a blocking finding is disputed.

**Wait for every review party to report before briefing any fix.** Merge findings into one numbered table: source, severity, finding, resolution — and send the developer exactly one fix brief per round (a second message mid-round makes the developer redo work). If one party overruns badly (more than twice the other's duration), send it one message asking for its findings so far and merge those. For XS deltas only the fresh reviewer runs (PIPELINE.md → *Size classes*). Product decisions already taken in `spec.md` are not defects; note them as resolved by decision. Findings about the project docs are fixed by the orchestrator in the docs.

**Resolution.** First separate *decisions* from *findings*: anything only the user can decide (product behaviour, privacy, scope, operational trade-off) is asked immediately in one AskUserQuestion, while the dev agent already works on the findings, so the answer is folded into the same fix round (PIPELINE.md ground rule 4). Blocking findings go to the responsible dev agent with the `implement-build` Phase 7 rules (the dev agent runs the affected tests; the orchestrator then runs the full gates once). Small items the orchestrator fixes itself (cosmetic residuals, one-line test tweaks, the outcome of a user decision when it is XS-sized) are batched into that same fix round: one edit pass, one gate run, one round-2 verification — never a separate gate run and review per item. Non-blocking findings are fixed when cheap, otherwise listed for the PR. Maximum two rounds; what is still open after round 2 goes into the PR as a known issue. The user is not involved.

**Parallel verification.** For S changes and S-sized feedback deltas, `implement-verify` starts together with round 1 (the diff is small and the gates are already green); for M/L it starts with round 2. **Round 2** is a read-only verification of the fixes by the same reviewer (resume it with one message) and is scoped to one question per finding: "does the fix resolve your finding as you stated it, and does it introduce anything new in the touched files?" — no new blast-radius pass, no fresh vendor-level proof unless the fix takes a different approach than the reviewer suggested. In both cases a blocking finding sends the affected ACs back for re-verification after the fix; non-blocking fixes that do not change rendered behaviour keep the existing evidence (note this in `evidence.md`).

Mark phase 8 `done` with rounds and timestamps; hand over to `implement-verify` (already started) and `implement-deliver`.
