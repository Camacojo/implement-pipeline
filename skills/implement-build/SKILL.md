Read `PIPELINE.md` in the `implement` skill directory (`../implement/PIPELINE.md` relative to this skill's base directory) first. Requires `spec.md`, `contracts.md` and `plan.md` (delta mode: also `feedback.md`, and only the ACs it marks as new/changed/defective are in scope). Writes `tests.md`, the code, and the results to `state.md`.

## Phase 6 — Tests first (defects and known interfaces only)

Tests are written before the code only for the test areas `plan.md` marks **tests-first** (PIPELINE.md ground rule 13: a defect, or a component whose interface already exists). For every other area the developer writes the tests with the code in Phase 7 under the same rules below; when no area is tests-first, mark the phase `skipped: new interface, tests with the code` and go to Phase 7.

Brief a test-author agent with `spec.md`, `contracts.md` (the identifiers and shapes it writes against) and the project's test conventions. When the plan's AC→test mapping spans two or more independent test areas with disjoint files (e.g. one service's tests vs. the tests of unrelated clients/handlers), brief one test author per area in the same message and let them run in parallel; each gets only its ACs and files. Rules for every test author (and for a developer writing tests with the code):

- One or more automated tests per AC in scope, using **only** identifiers, endpoints, selectors and fixtures named in the plan. Something missing → **stop and report**; the orchestrator amends the plan and re-briefs.
- Follow the project's test locations, naming and language conventions.
- Run the new tests and prove each **fails on its assertion**, not on syntax, import or setup errors; include the failing output per test in `tests.md`.
- Negative assertions must be discriminating (assert the decisive attribute/state before the action, not just "nothing appeared" right after it).
- Record AC → test file → test name in `tests.md`.
- Delta mode, defect items: first strengthen or add the test that exposes the defect and show it red; never weaken an existing assertion.

**The project's regression scripts are tests too.** When the project docs name regression scripts that run against the live application (API walkthrough, UI walkthrough), the checks for the new ACs follow the same tests-first rule: for a tests-first area a verify-script author is briefed in the same message as the test authors and writes them against `contracts.md` (endpoints, shapes, selectors, literal strings), runs the extended script once against the unchanged application and shows in `tests.md` that the new checks fail on their assertion while the existing ones still pass; for a new-interface area the developer of that layer writes them in Phase 7 as part of its package, and does **not** run the whole walkthrough — only the part the script lets it run alone, once, as its smoke check. Rules in both cases: extend the project's scripts, never start a new one; every new check names its AC; **every UI state that proves an AC gets a screenshot call** with the script's screenshot option, named after the AC, so Phase 9 needs no second pass for images; something the contracts do not name → stop and report. Phase 9 runs the scripts once, as gate and evidence (PIPELINE.md → *Verification has one layer*).

After this phase the tests-first tests are **frozen**: developers may fix setup or fixtures only with a written justification in `tests.md` and may never weaken an assertion. The same holds for regression-script checks written tests-first; a developer whose code makes a scripted check fail fixes the code, and reports a script defect (a wrong selector, a wrong expected value) with the evidence instead of editing the check. Tests written with the code are not frozen; the code review (Part A) judges them.

## Phase 7 — Implementation

- Brief each dev agent with `spec.md`, `contracts.md`, `plan.md`, its work package, the test files it must make pass — or, for an area that is not tests-first, the Phase 6 test rules, its ACs and the instruction to write the tests and its layer's script checks (with screenshot calls) in the package — and the project docs (relevant sections). **Name the project's smoke check** (its regression script and, for a UI change, the one navigation path that exercises the change the way a user reaches it) instead of letting each agent improvise one: dev agents that smoke-test a page with a direct reload miss the bugs that only appear when you navigate to it. Rules: follow the interface contracts exactly; follow project conventions; run lint/format/static analysis and **only the new and directly related test files** before reporting; rebuild/restart what the project docs require after source changes and wait with a blocking, timestamp-gated check; no files outside the package; no changes to frozen tests; report deviations from the plan explicitly, and append the report to `state.md`.
- Sequence packages in dependency order; run independent packages in parallel (one Agent call each, same message), with `isolation: worktree` when they share a repository. A work package holds application code, and for a new-interface area its tests and its layer's script checks; regression-script checks written tests-first in Phase 6 are not a package.
- Then the orchestrator runs the **fast gates** of every affected repository (ground rule 9): the full test suite, lint, static analysis, type check — the same set CI runs, per the project docs; if the docs list fewer gates than the CI workflow, run what CI runs and fix the docs. The regression scripts against the live application are **not** run here; they run once in Phase 9. Fix or delegate any failure. Nothing proceeds while something is red. Record the exact commands and counts.
- Hand over to `implement-review` **as soon as the fast gates are green** — ground rule 12: nothing else that is still running (a script, a report) holds the diff export or the reviewer briefs.

Mark phases 6–7 `done` with timestamps; hand over to `implement-review`.
